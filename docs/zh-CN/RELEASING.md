# 发布流程

English: [`../en/RELEASING.md`](../en/RELEASING.md)

研发母仓保存了内部证据和私人绝对路径，绝不能直接公开。

## 发布门禁

1. 单元测试、打包测试、disposable repo 测试和双语一致性检查全部通过。
2. 兼容矩阵不存在未经证据支持的声明。
3. 替换著作权和商标主体占位符。
4. 替换 `pyproject.toml` 中的公开仓库地址。
5. 净化导出中不存在内部报告、实验、私人路径、凭据、缓存或原始日志。
6. wheel 和源码包能够在全新临时环境中安装。
7. 精确公开提交具有 GPG 或 SSH 签名的附注标签，并在发布前通过本地标签验证。
8. 全新的只读独立验收者对精确候选提交和产物哈希返回 `PASS`。
9. 所有者另行确认 GitHub 与 PyPI 外部发布。

## 版本路径

```text
0.1.0-beta.1 -> 0.1.0-rc.1 -> 0.1.0
```

`0.1.0-beta.1` 支持合同包含七个已验证客户端。Gemini CLI、Roo Code 和 GitHub Copilot 继续作为仅适配器级的实验目标；在单独通过真实客户端与独立验收前，不得称为已支持。

## 发布顺序

1. 在仓库仍为私有时，推送净化候选与带签名的附注标签。
2. 保持 GitHub Release 为 Draft，并在已登录会话中验证发布说明和产物。
3. 取得所有者的明确授权，再将仓库转为公开。
4. 随即启用并验证私密漏洞报告；GitHub.com 只为公开仓库提供此功能。
5. 在不依赖已登录会话的条件下，验证源码、签名标签、安全策略和漏洞报告入口。
6. 发布并验证 GitHub prerelease，再匿名验证发布说明、产物和校验和。
7. 单独取得所有者对 PyPI 的批准，只上传一次，并验证在线项目页和安装路径。

`SHA256SUMS` 与 GitHub 资产摘要提供完整性证据，但不能替代签名标签，也不声明产物可跨构建环境逐字节复现。

## 外部边界

登录、账户变更、计费、签名身份、创建仓库、推送和发布软件包，必须在实际操作时再次获得明确确认。仅使用订阅内额度的测试授权不包含额外 credits 或 API 支出。
